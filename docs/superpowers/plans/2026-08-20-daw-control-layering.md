# daw-control: layering and disposition — implementation plan

**Goal:** Put the repository on the footing its Constitution already claims — a
portable core with per-host adapters, under the name and the organization that
match — and get the empirical answers that gate the track-policy and MIDI-map
features.

**Spec:** `docs/superpowers/specs/2026-08-20-daw-control-layering-design.md` —
read it alongside this plan. Decisions are recorded there and are not
re-litigated here.

**Roadmap ids:** `impl:primitive/layer-boundary` (in-flight),
`impl:gap/daw-control-rename`, `impl:gap/reaper-capability-probes`,
`design:feature/track-policy`, `design:feature/midi-map-backend`.

**Branch:** `feat/daw-control-layering` (pushed).

Steps use checkbox (`- [ ]`) syntax; tick them as they land.

## Global constraints

- No `any`, no `as Type`, no `@ts-ignore`; untrusted TOML/YAML/JSON validated,
  never cast. `@/` imports. ESM.
- **The layer boundary holds.** `tests/layering.test.ts` is the enforcement
  (Principle 7). New portable material goes in `src/core`; the REAPER-specific
  way to apply it goes in `src/adapters/reaper`. Weakening the test to make a
  change fit is the change being wrong.
- **A refactor moves no generated bytes.** Any restructuring proves it by
  building the keymap at the previous commit and at HEAD and diffing: identical,
  excepting the reload button's baked repo root and the version stamp.
- **REAPER behaviour is observed, not reasoned about** (CLAUDE.md). A claim
  about what an action or API call does is not admissible until a probe run
  records it.
- **Never write a file REAPER has open** (Principle 6). REAPER is running on this
  machine; probes use a throwaway `-cfgfile` so the live `reaper.ini` is never
  the file under test.
- `pnpm typecheck` and the full `pnpm test` before every commit. Commit at each
  coherent point and push (Principle 4).

## Task 1 — Rename to `daw-control` and transfer to `audiocontrol-org`

**Blocked on:** operator go-ahead. This is outward-facing and changes URLs.

**The hazard:** `src/adapters/reaper/ids.ts` salts every generated custom-action
ID with the literal `reaper-automation`. Changing it changes every `_<hash>`
SCR/ACT id in the keymap — a forced re-import, plus silent breakage of any
toolbar button bound to an old id. **The salt does not change here.**

- [ ] **Step 1: Prove the salt guard before touching anything.** Build the keymap
      and record its sha256. This is the artifact the rename must not disturb.
- [ ] **Step 2: Rename and transfer.**

      gh repo rename daw-control --repo oletizi/reaper-automation
      gh api -X POST repos/oletizi/daw-control/transfer -f new_owner=audiocontrol-org
      git remote set-url origin git@github.com:audiocontrol-org/daw-control.git

- [ ] **Step 3: Update the references that are genuinely the project's name** —
      `package.json` (`name`), `README.md`, `justfile`, `CLAUDE.md`. Update the
      cosmetic "Generated by reaper-automation" banner in the Lua templates only
      if you also accept a script-body diff (harmless: script bodies do not
      affect keymap bytes — see `install.ts`).
- [ ] **Step 4: Verify the salt survived.** Rebuild and compare sha256 against
      Step 1. A difference means the salt moved; revert rather than re-import.
- [ ] **Step 5: Leave the local checkout path alone** unless migrating
      deliberately. `stackctl` discovers its installation by walking up for
      `.stack-control/config.yaml` and is unaffected by a directory rename;
      Claude Code's per-project storage (`~/.claude/projects/-home-orion-work-
      reaper-automation/`, holding memory and transcripts) is keyed to the
      absolute path and would be orphaned.

## Task 2 — REAPER capability probes

**This is the real next work.** Three unknowns gate everything downstream, and
two of them decide whether a feature is possible at all.

**Harness:** REAPER 7.78 is at `/usr/local/bin/reaper` and is currently running;
`tower.local` (used by the razor-substrate plan) is not reachable from this
machine. Probes therefore run locally as a second instance:

    reaper -cfgfile /tmp/probe.ini -nosplash -new -newinst /tmp/probe.lua

- [ ] **Step 0: Settle the harness before trusting any probe result.** A fresh
      `-cfgfile` has no plugin scan, so `TrackFX_AddByName` would fail for
      reasons that have nothing to do with the question being asked. Decide
      whether to pre-seed a temp resource directory with the plugin caches
      (`reaper-vstplugins64.ini`, `reaper-jsfx.ini`) or point at the real
      resource dir with a throwaway ini. Record which, and why it cannot write
      the live `reaper.ini`. A probe whose harness is not understood produces
      evidence of nothing.

- [ ] **Step 1: Can ReaScript establish a MIDI-learn binding?** The load-bearing
      unknown: if this fails, the REAPER adapter can install the right plugins in
      the right order but cannot apply controller maps, and the MIDI half of the
      design needs a different mechanism.
      Suspected route: `TrackFX_SetNamedConfigParm(tr, fx, "param.<n>.learn.midi1", ...)`.
      Probe: insert a known FX, attempt the set, read back with
      `TrackFX_GetNamedConfigParm`, and dump the track chunk
      (`GetTrackStateChunk`) to see whether a `PARMLEARN` line appears. Record
      the exact accepted value format, or record that it is not settable.

- [ ] **Step 2: How tolerant is `TrackFX_AddByName` matching?** Decides what a
      role's per-platform resolution string must contain. Probe the same plugin
      via several spellings and record which return a valid index: bare name
      (`ReaComp`), FX-browser display name (`ReaComp (Cockos)`), format-prefixed
      (`VST3:4K EQ (Dusk Audio)`), and a partial. Include one plugin that is
      **not** installed and confirm the failure is detectable, since role
      resolution must fail loudly (Principle 2).

- [ ] **Step 3: Where does an inserted track land, and what is selected after?**
      Compare `InsertTrackAtIndex` against action `40001` with and without a
      track selection. Record placement relative to the selection, the resulting
      selection state, and whether the new track is armed. Placement becomes a
      policy field; the probe says which primitives can express it.

- [ ] **Step 4: Fold results into the design record.** Add rows to the
      "Verified while preparing this design" table and strike the answered
      entries from "Open empirical questions". An unrecorded probe result is a
      probe that will be re-run.

## Task 3 — Specify track policy (gated)

**Gate:** Task 2 Steps 2 and 3 answered and recorded.

Not specified here on purpose. What Task 2 returns determines whether roles can
be resolved by name, what a class can express about placement, and therefore what
the TOML surface should look like. Writing that surface first would be guessing.

Carried forward from the design record as inputs, not decisions:

- A role resolves per platform to an **ordered list** of plugins, not one.
- Three resolution tiers: acfx, open-source third party, stock Cockos fallback.
- Role resolution is checked at **build time** against the plugin caches, which
  is why it can fail loudly rather than at keypress.
- Bus creation semantics — folder-routed versus send-based submix — is an open
  question with a hole already cut for it: `mappings/luna.toml` carries
  `Cmd+Shift+B` "Create Bus", status `unmapped`.

## Task 4 — Specify the REAPER MIDI-map backend (gated)

**Gate:** Task 2 Step 1 answered.

Inputs from the design record:

- Descriptors are a **data contract** — JSON emitted by `acfx` from its constexpr
  parameter tables, read here as data. No package dependency.
- Bind parameters **by name**, resolved to an index through the descriptor at
  build time; a name absent from the descriptor is a build error.
- The descriptor owns units and ranges; the map owns only which control drives
  which parameter.
- `oletizi/audio-control` holds the YAML map corpus and the Ardour backend worth
  mining. Whether it is transferred and revived or mined and retired is undecided.

## Out of scope

- Convergence over already-open projects (design record, decision 7).
- Splitting `mappings/luna.toml` into portable and per-DAW tables (decision 3) —
  revisit when a second backend is actually being written.
- An Ardour adapter. The seam exists; nothing is built behind it.
