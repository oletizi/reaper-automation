# daw-control: layering, and where track configuration lives

Date: 2026-08-20
Status: design accepted (repository disposition and layer boundary); the track
policy and MIDI-map features it enables are not yet specified

## What prompted this

The starting request was "shortcuts and/or templates for creating new tracks with
pre-defined configuration". Three things turned that into a structural question.

**Templates are the wrong object.** The operator's actual statement of intent was
a set of invariants -- tape emulation and a channel strip on *every* track, master
tape and a bus compressor on *every* bus, in the manner of LUNA -- plus a
preference for infrastructure-and-policy-as-code over DAW template UIs, and a
requirement that definitions be portable across platforms and across DAWs. A
template is a snapshot stamped out at creation time; an invariant is a declared
desired state. The latter is what was asked for.

**REAPER cannot bind a template to a key anyway.** Track templates are files in
`<resource>/TrackTemplates/`. Action `46000` only opens a file dialog, and
individual `.RTrackTemplate` files receive no command ID -- confirmed by grepping
the 7.78 action dump for the template names installed on this machine, which
returns nothing. Binding a specific configuration to a key therefore requires a
generated script regardless of which declaration surface we choose, so the file
format buys nothing that offsets its costs.

**Captured template files do not travel.** The `.RTrackTemplate` files on this
machine were authored on macOS and reference `reaeq.vst.dylib`; the Linux install
of the same plugin is `reaeq.vst.so`. A capture-first approach fails at the
platform boundary, which is the boundary this project exists to erase.

## Prior art in the operator's own repositories

Two sibling codebases already implement most of the architecture this design
would otherwise have to invent.

**`oletizi/audio-control`** (cold since 2025-09) is a canonical vocabulary plus
per-DAW backends: `modules/canonical-midi-maps/` holds DAW-agnostic YAML with Zod
validation and a registry, `modules/ardour-midi-maps/` compiles those maps to
Ardour's `.map` XML, `plugin-descriptors/*.json` holds captured parameter lists,
and `tools/extract_vst_parameters.py` (Carla) plus `tools/juce-plugin-host/`
produce them. There is no REAPER backend.

**`audiocontrol-org/acfx`** is a cross-platform DSP platform whose README states
the discipline this design adopts: *"Dependencies point only inward
(`adapters/* -> core/*`; `core/*` depends on nothing platform-specific)"*, with
one parameter declaration driving a JUCE plugin, a desktop workbench, and
microcontroller firmware. Its `core/effects/` already contains `tape-dynamics`
(Jiles-Atherton hysteresis, with `wow-flutter` alongside in `modulated-delay`),
`compressor`, `program-dependent-saturation`, and `saturation` -- which is to say
the operator is building the very plugins the track policy wants to install.

## Decisions

### 1. This repository becomes `daw-control` under `audiocontrol-org`

The name `reaper-automation` describes a backend, while the Constitution's stated
end state -- one command that configures every DAW the operator uses -- describes
the whole. `audiocontrol-org` already houses the cross-target siblings (`acfx`,
`deskwork`, `production-control`, `videocontrol`) and the `*-control` naming
convention. Nothing in CONSTITUTION.md needs rewriting to survive the move, which
is itself evidence the repository already wanted to be that thing.

**Hazard: the repository name is load-bearing in exactly one place.**
`src/ids.ts` derives every generated custom-action ID as
`md5("reaper-automation/" + label)`, and those hashes are the `_<hash>` command
IDs written into the keymap. Changing that salt changes every SCR/ACT ID: a
forced re-import, and silent breakage of any toolbar button or hand-bound action
referencing an old ID. **The salt does not change during the rename.** If it is
ever changed it is a deliberate, separately documented act. The
"Generated by reaper-automation" strings inside the Lua templates are cosmetic and
safe to update, because a script-body change leaves keymap bytes untouched (see
`install.ts`).

### 2. One repository, with adapters -- not a repository per DAW

Keybindings, preferences, desktop key grabs, track policy and MIDI maps are one
thing from the operator's seat, share the resource-directory knowledge and the
dry-run/verify machinery, and are driven by one CLI. A split into
`reaper-control` / `ardour-control` against a published core would impose version
coordination on a single-operator project and buys nothing until a second backend
exists. Revisit when one does.

The one asset that plausibly earns its own repository later is the **map and
descriptor corpus**, because a data corpus grows on a different cadence than the
tool that reads it, and is the part another person might want to consume.

### 3. Split the code seam now; leave the data seam intact

The `core/` versus `adapters/` split in TypeScript is cheap, mechanically
enforceable, and costs nothing day to day. Splitting `mappings/luna.toml` into a
portable operation table plus a per-DAW binding table is a different proposition:
of its 111 bindings, 101 carry a REAPER-specific mechanism, so the split would
place every binding in two files joined by an operation id. That is a daily
ergonomic tax -- CLAUDE.md states that `mappings/luna.toml` is *the thing you
edit* -- in exchange for a benefit that does not exist until a second backend is
being written. Keep the table whole; let the code seam carry the discipline.

### 4. The core stays small and honest

Almost everything written so far is REAPER-specific, and the layering must say so
rather than flatter itself. Today's core is key-combo parsing, platform-target
translation, stable identifiers and the build stamp; the REAPER adapter holds the
action index, every Lua template, the ini handling, resource-dir resolution,
ReaTooled detection, the keymap emitter and the mapping parser. The core grows
when genuinely portable material arrives -- roles, track classes, descriptor
schemas, canonical maps -- not by relocating REAPER code across the line.

### 5. Plugin descriptors are a data contract, not a dependency

`acfx` declares each parameter once as a `ParameterDescriptor` (id, name, unit,
min, max, default, skew, kind, discrete choices) in a constexpr table that
`isValidDescriptor` static-asserts, so a malformed descriptor is a build error.
That table is a better source of truth than anything runtime extraction can
produce, and it is already versioned in a repository.

The seam is therefore **JSON descriptor files against an agreed schema**: `acfx`
emits its tables as a build artifact, `daw-control` reads them as data. No
package dependency, no C++/TypeScript coupling, no release coordination. This is
Principle 6 in its strongest form -- the values come from the program that owns
them -- and it is now recorded as a corollary of Principle 7.

Two consequences follow:

- **Bind parameters by name, resolved through the descriptor at compile time.**
  `audio-control`'s existing maps bind by bare index (`plugin_parameter: "5"`),
  a deliberate retreat from hallucinated names like `"Chorus.Mix"` recorded in
  its `plugin-descriptors/README.md`. Descriptors remove the reason for that
  retreat: a name absent from the descriptor becomes a build error, while an
  index is brittle across plugin versions and meaningless across plugins -- and
  role indirection ("the `drive` parameter of whatever fills the `tape` role")
  cannot be expressed with indices at all.
- **The descriptor owns units and ranges; the map owns only which control drives
  which parameter.** `acfx`'s `adapters/workbench/midi-binding.h` already states
  this invariant -- *"the binding stays parameter-agnostic"* -- while
  `audio-control`'s `ControlDefinition` duplicates range and scaling onto the
  mapping. Keep acfx's version.

Noted for `acfx` before the export exists: backlog task-7 records that
attack/release descriptors carry millisecond magnitudes while tagged
`ParamUnit::seconds`. Harmless internally; once descriptors are an interchange
format, the mislabel propagates to every consumer.

### 6. Roles resolve across three tiers, and may resolve to an ordered list

The operator has restricted the plugin set to open source. A role
(`tape`, `strip`, `bus-comp`) resolves per platform to one of:

1. **acfx** -- descriptor generated from source; strongest guarantees.
2. **Open-source third party** -- ChowTapeModel, Airwindows, LSP, Dusk Audio;
   descriptor extracted, but reproducibly, because anyone (including CI) can
   install the plugin and regenerate it. This is a substantive argument for the
   open-source constraint beyond licensing preference.
3. **Stock Cockos** -- ReaEQ/ReaComp/ReaXcomp as the always-available fallback on
   a machine with nothing else installed.

A role must be able to resolve to an **ordered list**, not a single plugin:
Airwindows plugins are deliberately single-purpose, and acfx splits tape,
saturation and compression across separate effects, so a `strip` will normally be
a chain.

Note that Analog Obsession -- for which `audio-control` already holds a CHANNEV
map -- is freeware but closed source and, as far as is known, ships no Linux
build. That map is macOS-bound and outside the current constraint.

### 7. Convergence is deferred, but the declaration shape preserves it

Reconciling an already-open project against the policy (report drift, add what is
missing) is explicitly *not* a requirement. The declarative shape is retained
anyway because it is free: a class stating "slots 1-2 are tape, strip" is already
desired-state, whereas "insert FX at index 0" would not be. Only the diff-and-
reconcile engine is dropped.

## Verified while preparing this design (REAPER 7.78, this machine)

| Claim | How checked | Result |
|---|---|---|
| Track templates have no bindable command ID | grep of `data/reaper-actions-7.78.tsv` for installed template names | no matches; only `46000` (dialog) and `42291` exist |
| Installed plugins are enumerable offline | read `reaper-vstplugins64.ini`, `reaper-jsfx.ini`, `reaper-fxtags.ini` | names, categories and developers all present and parseable |
| Captured templates are platform-bound | read `Actuality.RTrackTemplate` | references `reaeq.vst.dylib`; this machine has `reaeq.vst.so` |
| The ID salt is the repository name | read `src/ids.ts` | `md5("reaper-automation/" + label)` |

Offline plugin enumeration is the significant one: **role resolution can fail at
build time rather than at keypress**, which puts it on the same footing as the
existing command-ID validation and satisfies Principle 2 without a runtime probe.

## Open empirical questions

These gate implementation and must be answered by observation, not inference
(CLAUDE.md, "Verifying REAPER behavior").

1. **Can ReaScript establish a MIDI-learn binding?** Suspected route is
   `TrackFX_SetNamedConfigParm(tr, fx, "param.<n>.learn.midi1", ...)`. This is
   the load-bearing unknown: if it fails, the REAPER adapter can install the
   right plugins in the right order but cannot apply controller maps, and the
   MIDI half needs a different mechanism entirely.
2. **How tolerant is `TrackFX_AddByName` matching?** Whether format prefixes
   (`VST3:`), partial names, or exact FX-browser display strings are required
   determines what a role's per-platform resolution string must contain.
3. **Where does an inserted track land, and what is selected afterwards?**
   Placement relative to the current selection is a policy field, but the
   available primitives have not been checked.

## Not decided here

- The TOML surface for roles and classes.
- Bus creation semantics -- folder-routed versus send-based submix. Note that
  `mappings/luna.toml` already carries the hole: `Cmd+Shift+B` "Create Bus",
  status `unmapped`, commented *"REAPER buses are just folder tracks; wants a
  macro plus a naming decision."*
- Whether `oletizi/audio-control` is transferred and revived or mined and
  retired. Its durable assets are the YAML map corpus and the Ardour binding
  knowledge; the TypeScript around them is replaceable.
